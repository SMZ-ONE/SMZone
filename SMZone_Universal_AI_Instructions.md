# SMZone — Universal AI Instructions \& Project Manifesto

**Purpose:** This document is the absolute, uncompromised canonical instruction set for any AI assistant, coding agent, or development tool working on the SMZone project. Every AI must read, comprehend, and strictly follow this document before modifying, creating, deleting, or restructuring project files. These rules represent architectural decisions derived from historical project errors, specific e-commerce requirements, and future SaaS scalability—they must never be modified silently under the guise of "cleaner code."

\---

## 1\. Project Purpose, Vision, and Core Strategy

### 1.1 Project Identity \& Commercial Strategy

* **Project Name:** SMZone
* **Domain:** smzone.eu
* **Product Type:** AI-first Social Media Operating System designed specifically for e-commerce brands and SMEs.
* **Current Operational Focus:** The system is currently being built, tested, and optimized **exclusively for byCOSMETIQ** (Shopify store: `https://bycosmetiq.myshopify.com`), a natural and vegan cosmetics brand targeting the DACH market (Germany, Austria, Switzerland).
* **Long-Term SaaS Vision:** Once the system proves highly successful for byCOSMETIQ and creates a verified case study, it will be converted into a multi-tenant SaaS application hosted at `smzone.eu`. Therefore, the database, relationship matrix, and code architecture must be designed to support multiple brands via a `BrandProfile` model from Day 1, preventing heavy technical debt during the future multi-tenancy migration.
* **Interface Nature:** The system is an operational dashboard managed via Filament 4 for internal brand managers, content strategists, and marketing teams. It is NOT a public customer-facing interface.

### 1.2 Core Workflow Loop (The Social Media OS Architecture)

SMZone is not a simple social-media scheduler. The long-term objective is to build a centralized operating system through which a business can manage its complete social-media workflow seamlessly. The system must progressively reduce the amount of manual work required to operate a professional social-media presence across this exact operational pipeline:

```
Business
↓
Products / Services (Centralized Catalog)
↓
Content Ideas Generation
↓
AI Content Generation (Captions, Copy Variations, Media Assets)
↓
Media Processing / Libraries
↓
Content Planning (Visual Calendar Grid)
↓
Scheduling Engine
↓
Automated Publishing Pipelines
↓
Analytics Collection
↓
Performance / Revenue Attribution
↓
AI Learning \\\& Historical Optimization Loop
```

### 1.3 Core Language Strategy \& Segregation (Strict Rule)

* **Application UI \& Admin Panel:** The internal administrative backend application UI, including table headers, action buttons, form labels, and system notifications, is fully bilingual—supporting **only English (en) and German (de)**. There is NO Turkish language layer in the UI, translation files, or backend components.
* **AI Generated Content:** All marketing outputs generated by the AI (captions, copy variations, social media text blocks) must **ONLY be generated in German (de) or English (en)** depending on the targeted campaign parameters.
* **Mandatory Translation Engine:** Target language translation is non-optional and strictly enforced. Even if the incoming raw data scraped or synchronized from an external e-commerce store is in Turkish, mixed languages, or contains translation artifacts, the AI service must fully and cleanly translate the final marketing outputs into the selected destination language (German/English). Not a single foreign word may leak into the final client-facing caption.

## 2\. Technical Stack \& Strict Versioning Guardrails

Any AI assistant must inspect the actual installed dependency versions within the repository before introducing APIs or syntax. Never assume legacy methods apply.

* **PHP Version:** PHP 8.4+ only. Enforce strict typing on properties, method arguments, and explicit return types. Utilize modern features like constructor property promotion and typed class constants.
* **Framework:** Laravel 12+ only.
* **Reactive UI Layer:** Livewire 3.8.x+ only.
* **Admin Architecture:** Filament 4+ only.
* **Styling UI:** Tailwind CSS. Look and feel must be premium, minimalist, modern, clean, trustworthy, elegant, and highly operational. Avoid excessive gradients, unnecessary animations, visually noisy dashboards, excessive rounded cards, oversized typography, excessive shadows, or generic template-like designs.
* **Local Database:** SQLite (Managed via Laravel Herd).
* **Production Database:** PostgreSQL.
* **Asynchronous Execution:** Laravel Queues and dedicated Worker processes for all heavy external tasks.
* **Testing:** Pest Automation Framework for all unit, feature, and architecture tests.
* **Version Control:** Git + GitHub (Repository: `https://github.com`, Target branch: `main`).

## 3\. Development Philosophy \& Phased Roadmap

### 3.1 Build for the Long Term

* Every feature implementation must consider future multi-tenancy, complex API integrations, job queues, and analytics. Do not create short-term hacks that fix the current screen while making future SaaS migrations difficult.
* **The Lean Guardrail:** Do not prematurely implement heavy external features. Use clean abstractions and database stubs, but do not write real OAuth, live social media publishing pipelines, automated analytics collectors, or subscription billing layers before their designated development phase.

### 3.2 Detailed Development Phase Roadmap

The application must remain stable and working at the end of every individual phase. Never sacrifice application stability merely to move faster.

* **Phase 1 — Foundation:** Core Laravel framework setup, basic application layout structure, Git repository checkpointing, and foundational Filament administration panel dashboard. *(Completed).*
* **Phase 2 — Core Data (CURRENT OPERATIONAL PHASE):** Establishing strict database schemas for Products, Contents, Social Accounts, Settings, validation layers, casting, backing enums, and explicit local Eloquent relationship rules.
* **Phase 3 — Content Operations (CURRENT FUNCTIONAL FOCUS):** Building the interactive Content Planner interface, draft creation forms, multi-file element editing, layout filtering, scheduling foundations, and media asset storage stubs.
* **Phase 4 — AI Center (CURRENT FUNCTIONAL FOCUS):** AI Writer UI, AI provider abstraction layers, prompt layout architecture, isolated hashtag generation, product-aware context injections, brand voice integration matrices, and foundational AI learning models.
* **Phase 5 — Integrations:** Real OAuth provider authentication flows, live social account connections, and production Shopify e-commerce synchronization pipelines (Shopify platform context).
* **Phase 6 — Publishing:** Active Laravel Queues, automated scheduled publishing engines, platform retries, dead-letter failure handling, and detailed publication logs.
* **Phase 7 — Analytics:** Ingesting platform metrics, tracking post reach/engagement/clicks, separating platform metrics from internal metrics, and connecting content metrics to attributed e-commerce conversions/revenue.
* **Phase 8 — SaaS \& Multi-Tenancy:** Introducing workspaces/teams, tenant database ownership isolations, RBAC roles/permissions, onboarding wizards, and Stripe subscription billing.

## 4\. Laravel \& PHP 8.4 Coding Standards

### 4.1 General Code Architecture

* Always declare strict types explicitly at the very top line of every single PHP file: `declare(strict\\\_types=1);`
* Keep classes small and highly focused on a single responsibility.
* Avoid unnecessary global helpers, duplicated business code, dead code, or commented-out obsolete implementation blocks.
* **CRITICAL STRING INTERPOLATION RULE:** Never place ternary operators (`? :`) or complex logic directly inside `{$...}` placeholders within Heredoc or double-quoted (`"..."`) strings. PHP 8.4 will throw parsing exceptions. Always compute the result into a standalone variable before string construction.
* **Yorum Kültürü (Documentation Culture):** Complex, non-intuitive, or highly specific logical implementations must be thoroughly documented with Turkish comments explaining *why* the code was structured that way, ensuring future development cycles preserve historical context and past error resolutions.

### 4.2 Models and Eloquent Relationships

* Models must strictly represent domain entities and structural database relationships. Do not put large business workflows directly into Eloquent models.
* Move substantial business logic into dedicated Service classes.
* Make deliberate use of Eloquent casts, model-specific accessors/mutators when genuinely useful, and local model scopes where appropriate.
* Every model intended for factory-backed automated testing must explicitly implement the `use HasFactory;` trait.

### 4.3 Service Layer Architecture

* All substantial business logic (AI prompt evaluations, Shopify API processing, scraping engines, hashtag compilation, product synchronization) **MUST** reside exclusively in `app/Services/` (e.g., `AiContentService`, `HashtagService`, `ShopifyService`, `AnalyticsService`).
* Services must focus on one explicit domain responsibility. Avoid creating monolithic "God Services" containing unrelated workflows.
* Filament Resources, custom Pages, and Artisan CLI Commands must remain thin, lightweight orchestrators that call the respective service layer rather than re-implementing business workflows locally.

### 4.4 Error Management \& Defensive Programming

* Every single method reaching out to an external API (Gemini, Shopify, Scraping endpoints) must be encapsulated inside a clean `try/catch` block.
* Technical exception details and stack traces must be captured accurately using `Log::warning()` or `Log::error()`.
* Raw exception data or code stack traces must **NEVER** be displayed to the end operator.
* Service classes must expose internal non-fatal fallback issues via a `getLastError(): ?string` getter method so calling controllers/pages can send them to local logs, while displaying an understandable, actionable notification to the user interface.
* Never trust incoming user input or external scraped data blindly. Always apply defensive normalization rules (e.g., executing `ShopifyService::normalizeDomain()` to clean domain strings) before downstream usage.

## 5\. Filament 4 \& Livewire 3 Interface Standards

### 5.1 Filament 4 Implementation Guardrails

* Strictly enforce Filament 4 conventions. Never introduce Filament 3 syntax or legacy forms components. When uncertain, inspect current project conventions before writing code.
* Custom form pages (`Filament\\\\Pages\\\\Page`) must employ `Filament\\\\Schemas\\\\Schema` architectures instead of the legacy `Forms\\\\Form` namespace.
* Custom pages with forms must implement the `InteractsWithForms` trait along with the `HasForms` interface, and secure state bindings via `->statePath('data')`.
* Ensure navigation properties match the exact strict union types required: `string|BackedEnum|null` or `string|UnitEnum|null`.

### 5.2 Application Layout \& Navigation

* The Filament sidebar is split into three logical groups instead of one flat list, so day-to-day content work never mixes with brand configuration or system settings:

```
SMZ ONE - Content
├── AI Writer
├── Contents (Content Planner)
└── Products

SMZ ONE - Brand
├── Brand Center (the former "AI Center" hub page, repurposed as brand overview)
└── Brand Studio

SMZ ONE - Settings
├── AI Keys & Security
├── Social Accounts
└── Product Sync
```

* Dashboard remains outside all groups (Filament's default top-level item).
* Additional pages/resources must be placed inside one of these three existing groups rather than creating a flat, confusing sidebar or introducing a new top-level group without strong justification.
* Visual hierarchy across all pages must clearly communicate state changes: *What is happening? → What requires attention? → What can I do next? → What was the result?*
* Provide intuitive empty states detailing user next steps, clear loading states for heavy async components, and readable error cards.

### 5.3 Livewire 3 Reactivity Rules

* Livewire 3 drives the reactive component layer for interactive forms, dynamic UI, and asynchronous user actions. Avoid using custom JavaScript wrappers or raw asset scripts when native Livewire bindings solve the problem cleanly.
* Never let Livewire components swell into giant monolithic application classes. If operations become dense, pass the workflow downstream: `Livewire / Filament Page → Service/Action → Job (if long-running)`.
* All critical action buttons (Generate, Regenerate, Save, Synchronize) must implement double-submission protections using `wire:loading.attr="disabled"` backed by an explicit `wire:target`.
* Success or failure outcomes must always trigger a highly visible Filament `Notification` alert banner (success/danger/warning)—there are no silent success/failure states.

## 6\. Database, Security, and Configuration Rules

### 6.1 Database Relationships \& Relational Discipline

* Database design must represent the business domain rather than the current UI state. Use foreign keys, indexes, appropriate nullable constraints, explicit relationships, and unique constraints. Avoid storing relationships as arbitrary strings when a proper relational structure is appropriate.
* Operational logs and content assets (`ContentItem`) tied to catalog metadata (`Product`) must employ **`nullOnDelete()`** foreign-key configurations instead of `cascade` or `restrict`. If an item's profile is removed or unlinked on Shopify, historical marketing and content asset logs must be preserved in the DB.
* **Model-Schema Synchronization:** Every individual field mapped inside a model's `$fillable` array or explicit `$casts` dictionary must possess a matching physical database column created via a formal migration. Never introduce speculative fields in a model without a concrete database migration file.
* Use flexible JSON database columns cast natively to `array` properties for dynamic schema blocks such as `tags`, `forbidden\\\_words`, `preferred\\\_hashtags`, `brand\\\_keywords`, and `meta`.

### 6.2 Security, Credentials, and SSRF Defenses

* The `Setting` model natively encrypts secret API tokens, OAuth keys, and access credentials via custom Eloquent encryption casts (`encrypted`). Ayarlar **daima** `Setting::get()` / `Setting::set()` üzerinden okunur/yazılır.
* **CRITICAL SECURITY VIOLATION:** **NEVER** use bulk database queries like `Setting::query()->update(\\\[...])`. Mass updates completely bypass Eloquent hooks, lifecycle events, and model casting mechanisms, which will permanently encrypt-corrupt or destroy your encrypted tokens.
* Treat all user-supplied URLs for data scraping or enrichment as highly untrusted inputs. Defend aggressively against Server-Side Request Forgery (SSRF) by validating URL schemes, tracking hosts, evaluating resolved target IPs, and blocking local network ranges, loops (`127.0.0.1`, `localhost`), reserved addresses, and private subnets before executing external network fetch tasks. Never expose access tokens in UI, logs, exceptions, debug outputs, Git, or API responses.

## 7\. Content Engineering \& AI Safeguards (byCOSMETIQ Priorities)

### 7.1 AI Architecture \& Abstraction

* The UI layer should never need to know the implementation details of the AI provider. Maintain a clean abstraction hierarchy: `AI Center / AI Writer UI Component → AI Service → AI Provider Abstraction Interface → OpenAI / Gemini / Other Provider`. This allows providers to be replaced without rewriting the application UI.

### 7.2 Fact-Based Content Prompts

* AI text generation systems must function purely on a factual foundation. The engine must extract and utilize details found strictly within the database records (`Product` attributes, Shopify descriptions, confirmed materials, category data, or explicit ingredients parameters).
* The AI must never hallucinate company founders, fabricate country origins, fake production stories, or invent hypothetical benefits not supported by the product file context. Brand voice and story must not be derived from pure assumption. If the ingredients array is empty, the AI must omit any mention of ingredients entirely.
* CTA links must only be appended if a website URL is explicitly provided in the context, and only that specific domain may be used.

### 7.3 Hashtag Isolation Rules

* Social media hashtags must never be placed inline inside text copy or body paragraphs. They must be rendered completely separate from the core caption layout.
* To prevent compilation flaws from small or cheap LLMs (like `gemini-flash-lite`) ignoring prompt instructions, this rule is secured via code-level sanitization. The service must process all generated blocks through a backend regex sanitizer function (`stripInlineHashtags`) to strip loose hashtag tokens from the core body text before rendering.
* AI output text copy must be displayed inside a distinguished dark preview wrapper UI box styling (`bg-zinc-900`, `border-zinc-700`, `text-zinc-100`) to separate the AI's creative draft visually from standard management forms.
* **AI Learning Data:** All approvals, rejections, user edits, and performance histories must be treated as structured application data inside `AiLearning`, not as an uncontrolled collection of text prompts.

### 7.4 Core Data Models Mapping

* `Product`: Shopify sync local catalog. `shopify\\\_id` is the unique upsert key. Price, SKU, and stock are read exclusively from the **first variant** (multi-variant structure is not supported in the current phase).
* `ContentItem`: Represents canonical individual content assets. Field `status` maps to a backed enum `ContentStatus` (Draft, Scheduled, Published, Archived).
* `BrandProfile`: Manages brand voice and restrictions. JSON fields handle `forbidden\\\_words`, `preferred\\\_hashtags`, and `brand\\\_keywords`. Single active status loaded via `BrandProfile::activeForUser()`.

## 8\. Version Control, Automation Testing \& Agent Behaviors

### 8.1 Database Migration Discipline

* Database migrations are sequential historical ledgers. **NEVER** edit, overwrite, rename, or drop an old migration file that has already been committed or executed. Always construct a brand-new migration file to push structural alterations or type modifications. Check execution states via `php artisan migrate:status`.
* Never execute destructive reset operations like `php artisan migrate:fresh` without absolute local developmental certainty.

### 8.2 Testing Strategy

* Implement the Pest Automation Framework for all unit, feature, and integration testing.
* Prioritize testing coverage for Eloquent relationships, form validation hooks, backend service engines, external AI API abstractions, authorization layers, content state transitions, and critical UI behavior. Do not rely solely on manual UI clicking.

### 8.3 Universal AI Agent Behavior Protocols

* **Rule 1 — Inspect Before Modifying:** Always inspect the actual source code, related schema migrations, and resource controllers to understand the surrounding file conventions and dependencies before writing or changing code. Never overwrite code merely because another implementation appears cleaner.
* **Rule 2 — Preserve Architecture:** If an established architecture pattern exists and is consistent with the project vision, extend it. Do not introduce competing code styles or secondary architectures.
* **Rule 3 — One Canonical Model:** Ensure there is only one authoritative domain model for core units (`ContentItem`, `Product`, `SocialAccount`). If duplicates are discovered, stop and determine which is canonical before deleting anything.
* **Rule 4 — No Silent Destruction:** Never silently delete project assets, alter core structural definitions, rename domain concepts, or remove system components without detailing the complete downstream impacts first.
* **Rule 5 — Minimal Changes:** When fixing a problem, modify only what is necessary. Avoid unrelated refactoring during feature work.
* **Rule 6 — Verify:** After meaningful changes, verify using the appropriate artisan command, application URL, automated test, and git diff. Never claim a feature works without verification.
* **Rule 7 — Communication Flow:** Keep individual tasks small and incremental. Match code changes with the standard development checkpoints: 🎯 Goal → 💻 Command(s) → ✅ Test → 💾 Commit → ☁ Push. Do not give long explanations before the user has executed the previous step.
